ТЕХНИЧЕСКОЕ ЗАДАНИЕ И ПЛАН ЭТАПОВ v5
Проект: рабочий стол Fedora Linux + Hyprland + Quickshell
=========================================================

Этот файл заменяет PLAN_V4.txt. Все решения из ответов на открытые вопросы
зафиксированы здесь. Файл написан так, чтобы его можно было передать
модели целиком и вести проект по этапам.


0. ПРАВИЛА РАБОТЫ (обязательны для любой модели)
-------------------------------------------------
- Код, файлы и установка программ выполняются только по отдельной команде
  владельца проекта. До команды работаем только с описанием и планом.
- Работаем по этапам. Этап не начинается, пока предыдущий не проверен.
- Каждый этап заканчивается проверкой по критерию из описания этапа.
  Если критерий не выполнен, этап не закрываем, а записываем причину.
- Пароли, токены и приватные данные нигде не сохраняются и не
  попадают в логи, темы и конфиги.
- Механизм проверки пароля (PAM) не меняется и не переписывается.
- Ошибка оформления не должна блокировать вход в систему.
- Экспериментальные плагины необязательны: система работает без них.
- Версии Hyprland, Quickshell, SDDM и плагинов фиксируются в versions.txt.
- Любое изменение, которое может сделать систему неработоспособной,
  выполняется только после резервной копии и проверки отката.
- Если модель сомневается, она задаёт вопрос, а не угадывает.


1. ЗАФИКСИРОВАННЫЕ РЕШЕНИЯ
---------------------------
1.1 Календарь. Полноценный виджет: дата, время, погода, праздники, события,
    поддержка нескольких часовых поясов. Каждый дополнительный элемент
    можно отключить.
1.2 Сцены. Стартовый набор из пяти сцен:
    - Aurora Glass (главный визуальный стиль);
    - Cyber Terminal (терминалы и системная информация);
    - Developer Workspace (программирование);
    - Gaming Mode (игры и производительность);
    - Cinema & Music (музыка и мультимедиа).
    Пользователь может создавать неограниченное число своих сцен, менять
    готовые и экспортировать любую сцену.
1.3 Браузер. По умолчанию Firefox. Все функции работают с Chrome, Chromium,
    Brave и другими браузерами через MPRIS. Система не привязана к одному браузеру.
1.4 Первый визуальный эффект: Liquid Glass + Spring Physics.
    Блики, прозрачность, мягкое свечение, плавное движение, пружинная физика.
    Все параметры настраиваются. Нужен упрощённый вариант для слабого
    оборудования (тот же эффект без свечения и с меньшим разрешением).
1.5 Первый экспериментальный модуль: Window Physics.
    Начинаем с Elastic Resize и Wobbly Windows. Focus Lens идёт следующим
    экспериментальным модулем.
1.6 Игровой режим. Гибридная схема:
    - при запуске игры отключаются тяжёлые эффекты, экспериментальная физика
      и фоновые анимации;
    - отдельно существует безопасная конфигурация Hyprland без экспериментальных
      плагинов, она нужна только для восстановления после ошибок;
    - игровой режим и аварийное восстановление не путаются: это разные механизмы.
1.7 Экран входа. Менеджер входа SDDM с собственной QML-темой. Цели: анимированные
    фоны, настраиваемые поля пароля, аватары, кнопки, плавные переходы.
    Обязательно: независимый безопасный способ вернуться к стандартной теме входа.
1.8 Мониторы. Архитектура сразу рассчитана на несколько мониторов: у каждого
    свои обои, панели, виджеты, масштаб и расположение рабочих пространств.
    Первую проверку делаем на одном мониторе.
1.9 Общие требования:
    - всё максимально настраивается через графический интерфейс;
    - ни одна функция не ограничивает пользователя готовыми сценами,
      эффектами или профилями;
    - совместимость с AMD и NVIDIA обязательна;
    - экспериментальные плагины необязательны.


2. ЗАМЕЧАНИЯ И РИСКИ (их нужно учесть до старта)
------------------------------------------------
2.1 Wobbly Windows сложнее Elastic Resize. Это сетка вершин окна с пружинами
    и демпфированием, плюс корректный ввод. Поэтому порядок внутри модуля
    Window Physics: сначала Elastic Resize (проверка), затем Wobbly (тоже проверка
    на каждом шаге). Если Wobbly не получается стабильным, Elastic остаётся
    рабочим, а Wobbly откладывается. Это не отказ от решения, а проверка.
2.2 Экран входа работает до запуска Hyprland, поэтому блюр и эффекты Hyprland
    там недоступны. Liquid Glass на экране входа пишется на QML внутри темы SDDM.
    Визуально будет похоже, но реализация другая, это надо держать в голове.
2.3 Liquid Glass на экране входа и в сессии это два разных кода. Их делаем
    отдельно, но от одной палитры токенов.
2.4 "Игровой режим" и "аварийное восстановление" разные. Первый включается
    по событию игры, второй по маркеру аварийного выхода. Нельзя, чтобы
    одно срабатывало вместо другого.
2.5 Несколько мониторов проектируем сейчас, но тестируем позже. Пока
    архитектура это учитывает, код на одном мониторе не должен ломать
    будущую поддержку.


3. СТРУКТУРА ЭТАПОВ
--------------------
Для каждого этапа: цель, что делаем, проверка, модель, откат.
Модели (рекомендация, решает владелец проекта):
  Haiku 5.5  - документация, списки, простые конфиги.
  Sonnet 5.5 - основная разработка.
  Opus 5.5   - архитектура, ревью, критичные места.
  Fable 5.2  - шейдеры, C++-плагины, ревью пути входа, финальный аудит.


ЭТАП 0. ПОДГОТОВКА
  Цель: репозиторий и документы готовы, код ещё не начат.
  Делаем:
    - репозиторий dotfiles с папками hypr, quickshell, sddm, docs;
    - README.md с описанием проекта и порядком установки;
    - versions.txt с проверенными версиями;
    - install.sh как черновик, без запуска.
  Проверка: репозиторий открывается, структура совпадает с описанием.
  Модель: Haiku 5.5 (документы), Sonnet 5.5 (схема токенов).
  Откат: не нужен, это только файлы в репозитории.


ЭТАП 1. HYPRLAND: БАЗА И БЕЗОПАСНАЯ СЕССИЯ
  Цель: Hyprland работает, есть запасная сессия без плагинов.
  Делаем:
    - hyprland.conf, monitors.conf, input.conf, keybinds.conf;
    - скругления, блюр, тени, встроенные анимации;
    - симлинки из репозитория в ~/.config;
    - вторая сессия "Hyprland (safe)": минимальный конфиг, без плагинов
      и Quickshell, простые обои;
    - обёртка запуска сессии: маркер "сессия начата", штатный выход
      снимает маркер, аварийный оставляет. При маркере следующий вход
      стартует safe-сессию с уведомлением;
    - атомарная запись файлов состояния (сначала временный файл, потом переименование).
  Проверка:
    - сессия стартует, hyprctl configerrors пустой;
    - аварийный выход приводит к safe-сессии при следующем входе;
    - штатная перезагрузка не приводит к safe-сессии.
  Модель: Sonnet 5.5 (конфиги), Opus 5.5 (ревью обёртки и маркера).
  Откат: переключение входа на сессию "Hyprland (safe)" или Plasma.


ЭТАП 2. QUICKSHELL: КАРКАС И ХОЛСТ ВИДЖЕТОВ
  Цель: виджеты живут на холсте на фоновом слое.
  Делаем:
    - фоновый слой поверх обоев, под окнами;
    - холст: мир большого размера, камера (сдвиг, масштаб);
    - панорамирование пустым местом, масштаб колесом;
    - режим редактирования: перетаскивание и размер только здесь;
    - координаты виджетов в JSON по каждому монитору (архитектура под
      несколько мониторов, пока один);
    - панель сверху: часы, рабочие пространства, статус.
  Проверка:
    - окна кликаются, фон не перехватывает ввод;
    - виджеты стоят на месте при панорамировании;
    - позиции сохраняются после перезапуска и после аварийного выхода.
  Модель: Sonnet 5.5 (QML), Opus 5.5 (ввод и слой фона).
  Откат: возврат к предыдущей версии конфига через git.


ЭТАП 3. ОБОИ
  Цель: обои меняются и работают у каждого монитора отдельно.
  Делаем:
    - статичные обои из папки, смена по хоткею;
    - видео-обои через mpv с аппаратным декодированием (VAAPI на AMD,
      NVDEC на NVIDIA, выбор по gpu-конфигу);
    - выбор обоев: сетка превью по хоткею;
    - обои фиксированы на экране и не двигаются с холстом.
  Проверка: смена обоев сохраняется; видео играет с низкой нагрузкой CPU.
  Модель: Haiku 5.5 (сетка), Sonnet 5.5 (mpv и декодирование).
  Откат: статичные обои по умолчанию.


ЭТАП 4. ЦВЕТА И ТЕМЫ
  Цель: палитра берётся из обоев, каждый виджет можно перекрасить.
  Делаем:
    - извлечение доминирующих цветов из картинки и первого кадра видео;
    - палитра применяется ко всему интерфейсу;
    - ручной override палитры на каждом виджете, не сбрасывается при смене обоев;
    - Ctrl+Alt+F: готовые темы и режим "из обоев";
    - Theme Engine: параметры визуала как данные с версией схемы.
  Проверка: смена обоев меняет палитру; override на виджете сохраняется.
  Модель: Opus 5.5 (токены и визуальная система), Sonnet 5.5 (извлечение цветов).
  Откат: возврат к стандартной палитре.


ЭТАП 5. ВИДЖЕТЫ
  Цель: набор виджетов работает и подчиняется токенам темы.
  Делаем:
    - каркас виджета: использует только токены;
    - часы и дата;
    - календарь: дата, время, погода, праздники, события, несколько часовых
      поясов, каждый элемент отключаем;
    - системный монитор: CPU, RAM, GPU (sysfs для AMD, nvidia-smi для NVIDIA);
    - плеер (MPRIS): обложка, управление, прогресс, тексты песен
      по кнопке через LRCLIB с локальным кэшем, очистка заголовков YouTube,
      правило "последний активный плеер";
    - быстрые настройки: Wi-Fi, Bluetooth, звук, яркость, VPN, питание;
    - буфер обмена с историей;
    - единый лаунчер с режимами: приложения, команды, калькулятор, файлы;
    - индивидуальная настройка каждого виджета: материал, движение, эффекты,
      режимы "простой" и "расширенный".
  Проверка: каждый виджет работает отдельно; плеер управляет Firefox
  или Chrome с SoundCloud и YouTube; календарь переключает города.
  Модель: Sonnet 5.5 (виджеты), Haiku 5.5 (очистка заголовков, простые правила).
  Откат: виджет отключается в настройках, остальные не затрагиваются.


ЭТАП 6. СЦЕНЫ, ПРОФИЛИ, ИГРОВОЙ РЕЖИМ
  Цель: переключение между сценами мгновенно, игры не мешают работе.
  Делаем:
    - сцена на рабочее пространство: виджеты, камера, тема, уровень;
    - пять стартовых сцен из раздела 1.2, создание и экспорт своих;
    - переключение по хоткею без меню, 100–150 мс или без анимации;
    - режим "только работа": прячет игровые виджеты;
    - перенос игр в спецпространство при переходе в работу;
    - игровой режим: при запуске игры отключаются тяжёлые эффекты,
      экспериментальная физика и фоновые анимации (см. 1.6);
    - конфиг как данные: JSON с версией схемы, миграции старых сцен.
  Проверка:
    - переключение сцены мгновенное;
    - при запуске игры нагрузка снижается, при выходе возвращается;
    - аварийное восстановление не срабатывает от игрового режима.
  Модель: Sonnet 5.5 (сцены и хоткеи), Opus 5.5 (схема данных и игровой режим).
  Откат: возврат к стандартной сцене Aurora Glass.


ЭТАП 7. ВИЗУАЛ: LIQUID GLASS И SPRING
  Цель: первый узнаваемый визуальный эффект работает и настраивается.
  Делаем:
    - Liquid Glass на виджетах и панелях: блики, прозрачность, мягкое свечение;
    - Spring Physics на движении виджетов;
    - все параметры регулируются;
    - упрощённый вариант для слабого железа;
    - пресеты Balanced, High, Ultra (уровень нагрузки, не конкретная карта);
    - Performance Director выбирает уровень по нагрузке и режиму;
    - проверка совместимости эффектов: несовместимое отключается с сообщением;
    - визуальный принцип стола зафиксирован первым (один принцип материала,
      одна система движения, одна палитра от обоев).
  Проверка: эффект виден и плавный; упрощённый вариант работает;
  переключение пресетов не ломает интерфейс.
  Модель: Fable 5.2 (шейдеры Liquid Glass), Opus 5.5 (система движения и
  совместимость), Sonnet 5.5 (Spring в QML).
  Откат: вернуться к пресету Balanced или выключить эффект.


ЭТАП 8. ПРОДВИНУТОЕ (без C++)
  Цель: полезные функции без экспериментальных плагинов.
  Делаем:
    - Smart Tiling на Dwindle и Master, шаблоны раскладок через скрипт;
    - правила окон через GUI (прозрачность, блюр, анимация открытия);
    - терминал по хоткею в спецпространстве;
    - громкость по приложениям и выбор устройства (wpctl);
    - скриншоты и запись экрана с редактором в теме;
    - экспорт и импорт профиля одним файлом;
    - мировые часы;
    - уведомления в палитре стола;
    - отмена и повтор для тем и раскладки;
    - редактор горячих клавиш с проверкой конфликтов;
    - обзор рабочих пространств, если готового достаточно.
  Проверка: каждая функция работает отдельно и отключается.
  Модель: Sonnet 5.5 (большинство), Haiku 5.5 (простые правила и шаблоны).
  Откат: каждая функция выключается отдельно.


ЭТАП 9. ЭКСПЕРИМЕНТАЛЬНЫЕ ПЛАГИНЫ (необязательные)
  Цель: необычные эффекты окон без влияния на базовую систему.
  Условие: стол работает без плагинов, все плагины можно отключить.
  Первый модуль: Window Physics.
    9.1.1 Elastic Resize (инерция краёв). Проверка: ресайз плавный,
          ввод работает по исходной геометрии.
    9.1.2 Wobbly Windows (сетка с пружинами). Проверка: деформация
          визуальная, клики попадают в исходный прямоугольник, нет зависаний.
          Если не стабильно, откладываем, Elastic остаётся.
  Далее по очереди: Focus Lens (следующий модуль), затем Window Visual
  Effects, Workspace Transitions (один простой переход), Window Deformation
  (Magic Lamp и другие), Dissolve и Shatter, Gravity Drop и Magnetic Edges.
  Правила:
    - каждый плагин собирается под конкретную версию Hyprland (hyprpm);
    - игровой режим переключает настройки плагина, а не выгружает его;
    - после N подряд сбоев плагин выключается автоматически;
    - менеджер экспериментов в Quickshell: включение, версии, журнал, откат.
  Модель: Fable 5.2 (код плагинов и ревью рендеринга), Opus 5.5 (архитектура
  менеджера), Sonnet 5.5 (интерфейс менеджера).
  Откат: отключение плагина в менеджере и возврат к предыдущему коммиту.


ЭТАП 10. ТЕСТОВЫЙ СТЕНД
  Цель: проверять изменения без риска для основной сессии.
  Делаем:
    - вложенный запуск Hyprland внутри рабочей сессии;
    - виртуальная машина для проверки входа и тем;
    - чек-лист после каждого этапа;
    - неделя ежедневного использования перед каждым новым слоем.
  Проверка: стенд запускается, чек-лист заполнен.
  Модель: Sonnet 5.5 (стенд и скрипты), Opus 5.5 (план тестов).
  Откат: не нужен.


ЭТАП 11. ЭКРАН ВХОДА (SDDM, QML-тема)
  Цель: красивый экран входа, стандартный вход не затронут.
  Делаем:
    - исследование: актуальная версия SDDM на Fedora, совместимость с Hyprland
      и Plasma, пробный вход в виртуальной машине;
    - тема входа: QML, фон (статичный по умолчанию, анимированный и видео
      по выбору), поле пароля (форма, цвет, прозрачность, иконка, подсветка,
      анимация), аватары и карточки, кнопки выключения, перезагрузки и выбора
      сессии (Hyprland или KDE Plasma);
    - Liquid Glass на экране входа (QML-шейдер, та же палитра токенов, что в сессии);
    - анимации: появление, переключение пользователя, успешный вход
      (не задерживает вход дольше примерно 1 секунды);
    - экспорт токенов в theme.conf темы входа;
    - валидатор тем: синтаксис, запрещённые вызовы, размер ассетов, без сети;
    - стандартная тема всегда установлена и не удаляется;
    - независимый способ возврата к стандартной теме: выбор темы в конфиге
      меняется обратно, запасной вход через консоль (Ctrl+Alt+F2),
      загрузка с live-флешки;
    - редактор экрана входа с предпросмотром (предпросмотр не проверяет пароль).
  Запреты:
    - сторонние плагины и сторонний QML на экране входа не запускаются;
    - тема без сетевого доступа;
    - PAM и проверка пароля не меняются;
    - пароль не сохраняется в теме.
  Проверка:
    - тема работает в виртуальной машине;
    - битая тема не блокирует вход: вход поднимается со стандартной темой;
    - возврат к стандартной теме работает за минуту;
    - вход в Hyprland и в KDE Plasma работает.
  Модель: Opus 5.5 (исследование и архитектура), Sonnet 5.5 (QML-тема),
  Fable 5.2 (шейдеры и ревью пути входа), Haiku 5.5 (документация).
  Откат: переключение на стандартную тему SDDM.


ЭТАП 12. ЭКРАН БЛОКИРОВКИ (hyprlock)
  Цель: блокировка в той же палитре, что и остальная система.
  Делаем:
    - тема блокировки отдельно от темы входа;
    - генерация конфига hyprlock из текущей темы, без ручной правки;
    - та же палитра токенов, что на экране входа.
  Проверка: блокировка открывается и разблокируется; палитра совпадает
  с темой стола.
  Модель: Sonnet 5.5 (генератор), Haiku 5.5 (проверочный чек-лист).
  Откат: стандартная тема hyprlock.


ЭТАП 13. НЕСКОЛЬКО МОНИТОРОВ
  Цель: архитектура работает с несколькими экранами.
  Делаем:
    - у каждого монитора свои обои, панели, виджеты, масштаб, расположение
      рабочих пространств;
    - тестирование сначала на одном мониторе, затем на двух;
    - поведение экрана входа на нескольких мониторах (проверить).
  Проверка: два монитора работают независимо; конфиг одного монитора не
  ломает другой.
  Модель: Opus 5.5 (архитектура мониторов), Sonnet 5.5 (реализация).
  Откат: работа только на основном мониторе.


ЭТАП 14. СОВМЕСТИМОСТЬ AMD И NVIDIA
  Цель: смена видеокарты не требует переделки конфигов.
  Делаем:
    - один файл gpu.conf с настройками GPU;
    - install.sh с выбором amd или nvidia;
    - мониторинг через адаптер (sysfs или nvidia-smi);
    - видео-профили: VAAPI на AMD, NVDEC на NVIDIA.
  Проверка: переход по инструкции GPU_SWITCH.txt проходит без переписывания
  конфигов.
  Модель: Sonnet 5.5 (скрипты), Opus 5.5 (ревью инструкции смены GPU).
  Откат: возврат к AMD по GPU_SWITCH.txt.
